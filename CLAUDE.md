## Working relationship

Claude acts as **game design and programming partner**. The user is a software architect with deep web, database, and .NET/C# experience but little game-design or Godot experience. That means:

- Explain Godot and game-dev concepts when they come up, mapping them to .NET/web ideas where that helps (scenes ≈ composable components/prefabs, signals ≈ C# events, autoloads ≈ singleton services, Resources ≈ serializable data objects/config).

- On design questions, give a recommendation with reasoning (genre conventions from Brotato / Vampire Survivors are a good reference), not just a list of options. Flag decisions that are expensive to reverse later.

## Project state

Playable prototype: mode select (Arcade / Career) → class select (Fighter, Mage, Warlock, Necromancer) → (career: talents screen) → pick 3 of the class's 8 spells → 20-wave run (`Main.TotalWaves`) with gold drops and a between-wave shop of stat items. Career characters level up between runs and save to `user://career.json`. Characters, enemies, minions and coins use placeholder SVG sprites (`art/`); projectiles, pickups and effects are still shapes drawn with `_Draw()`.

- **Engine:** Godot 4.7, **.NET (C#) build** (`/Applications/Godot_mono.app`). Assembly name `ArenaShooter`. Write gameplay code in C#, not GDScript, unless there's a specific reason.
- **Renderer:** currently `mobile`, with Jolt set for 3D physics (scaffold defaults). The game is 2D; revisit the renderer choice (Forward+ / Compatibility) before relying on renderer-specific features.
- **.NET:** the project targets `net10.0` (LTS, supported to Nov 2028). SDK 10.0.402 is installed at `/usr/local/share/dotnet`. The Godot editor builds with the SDK under `/usr/local/share/dotnet` even when `DOTNET_ROOT` points elsewhere, so a future .NET upgrade needs Microsoft's installer there. A user-local SDK isn't enough for the editor.

## Commands

`$GODOT` is the Godot .NET binary: `/Applications/Godot_mono.app/Contents/MacOS/Godot` on the user's Mac, plain `godot` in the cloud (see below).

```bash
$GODOT -e --path .                  # open the editor on this project
$GODOT --path .                     # run the main scene
$GODOT --path . res://path/to/scene.tscn   # run a specific scene
$GODOT --headless --path . --import # re-import assets / regenerate .godot cache (needed once in a fresh clone)
dotnet build                        # compile C#
$GODOT --headless --path . --quit-after 400   # smoke test: surfaces runtime errors in stderr
```

## Testing

No test framework yet. Verify features by running the game and reading logs. Check how you're running first: the user's Mac has the editor, a display and ffmpeg; a cloud session is headless Linux with only .NET and Godot.

### Autoplay (works everywhere)

`--autoplay` (after `--`) plays a whole run unattended through the real UI. It presses the mode-select (Arcade unless `--mode=career`), class-select, spell-select and shop buttons, circles the arena collecting coins, logs `[autoplay] event key=value` lines and quits when the run ends. A normal launch ignores it. Flags (full list in `scripts/debug/AutoplayOptions.cs`):

```bash
# Uncapped: about 30x real time on the Mac (a full 20-wave run = ~19 min of game time in ~35s; a wave-5 death ~8s). grep the log for results.
$GODOT --headless --path . --fixed-fps 60 --disable-vsync --quit-after 90000 -- --autoplay --class=mage --seed=1 --move=smart --shop=smart
#   --class=NAME|INDEX  --spells=A,B,C (picks, in slot order; default the list's first N)  --wave=N (start wave)  --waves=N (run length; default 20)  --seed=N (same seed = identical run, for before/after)
#   --god  --shop=cheapest|first|skip|smart|random  --move=circle|still|smart  --autocast (all spells, incl. manual ones)
#   --bot-aggression=0..1 (default 0.5)  --bot-danger=PIXELS (default 60): tuning for --move=smart
#   --item="Rabbit's Foot" (repeatable; gear is equipped)  --stat=CritChance:20 (repeatable)
#   --rarity=common|uncommon|rare|epic (every shop offer and --item grant gets this rarity instead of a roll)
#   --buy-potion="Potion of Fury" (repeatable; buys one per shop visit before other buys; --item grants potions too)
#   --menu-delay=SECONDS (wait before each menu click, so Movie Maker records the shop)
#   --mode=arcade|career (default arcade)  --save=PATH (career save; default user://career_autoplay.json, never the real one)
#   --reset-career (delete that save first)  --reset-character (career: Reset character on the talents screen: ask, cancel, ask, confirm; logs career_reset)  --runs=N (N runs in one launch via the real restart; run k uses seed+k)
#   --talents=spread|none  --heirloom=priciest|keep (career: how to spend points / what to keep after a victory)
#   --retry (with --runs: later runs start via the end screen's "Retry same class", skipping the select screens)
#   --tour (1s into the first wave: Tab gear screen open/close, Esc pause menu → Settings → flip Damage numbers → Back → Resume)
#   --settings=PATH (settings file; default none: Autoplay uses default settings in memory and never writes user://settings.cfg)

# Career progression in one launch against a scratch save (or separate launches without --runs, to test reloading the file):
$GODOT --headless --path . --fixed-fps 60 --disable-vsync --quit-after 270000 -- --autoplay --mode=career --class=fighter --seed=1 --save=<scratch>/c.json --reset-career --runs=3 --waves=5
```

**Movement:** `--move=circle` (the default) follows a fixed circle and never dodges, so it plays like a weak player and dies by wave 2–3. `--move=smart` (`scripts/debug/SteeringBot.cs`) steers by context steering: each frame it scores 16 directions for interest (coins, hearts, the ring at its preferred distance from the nearest enemy) and danger (enemies about to touch, enemy shots on a collision course, spawn markers, walls) and takes the most interesting safe one. The preferred distance comes from the equipped weapon (`MeleeArcAbility` → 0.7 × reach, else 0.8 × range), so every class works without its own profile, and it kites under 35% HP. Results measure this bot, not a player: use them to compare (class vs class, before/after a change) and keep its logic unchanged while comparing; if you change it, rerun both sides.

**Shopping:** `--shop=cheapest` (default) buys the cheapest offer until broke: no judgment, never rerolls, so it's for testing that things work. `--shop=smart` (`scripts/debug/ShopBot.cs`) values offers with per-stat weights for the class (Attack Speed, Cooldown Reduction and Minion Damage weighted by the weapon, spell and minion shares of the run's damage; Life Steal only if it steals life, Minion Damage only with minions, nothing past a cap; weapons by DPS vs. the starting weapon), subtracts what an item would replace, buys the best value per gold, rerolls up to 4 times, then buys health potions. `--shop=random` buys/rerolls/stops at random from its own seeded generator, to explore the item space. Use smart to compare spells and classes, random to measure items (smart's weights would bias item results). Spells that are manual by default (Charge, Blink, leaps) are never cast by Autoplay without `--autocast`, so always pass it when comparing spells.

**Build sweeps:** `tools/sweep.py` (Python 3, standard library) plays every 3-spell combination of each class (56 per class) with `--move=smart --autocast` and ranks them. `run` writes one log per build and resumes an interrupted sweep; `report` prints per class the spell lift (average waves cleared with vs. without the spell), damage share per spell, best and worst builds, and with random-shop logs an item lift table (items bought in the first `--item-window` shops, among runs that got that far, to limit survivorship bias; compared within each class, so class-only items aren't blamed for a weak class). At 20 waves a full sweep (224 builds × 5 seeds) takes roughly an hour on the Mac; run it in the background.

```bash
tools/sweep.py run <scratch>/sweep --runs 5 -j 9                     # every class; --classes mage to narrow
tools/sweep.py run <scratch>/sweep-items --runs 3 -j 9 --shop random
tools/sweep.py report <scratch>/sweep --json <scratch>/sweep.json
```

**Balance passes (keep them short).** Each launch is single-threaded and `-j 9` already fills the Mac's 10 cores, so the speedup is simulating less, not more parallelism. Class parity is measured on each class's top 20% of builds (`report` ends with that table; see `Goals.md`).
1. Baseline: reuse the last full sweep's `--json` if the game hasn't changed since; otherwise one full sweep (`--runs 3`, ~1 h).
2. While tuning, check only the top builds: `tools/sweep.py run <scratch>/q1 --top 11 --from <scratch>/sweep.json --seed 101 --runs 2` (`--classes` for the ones you touched; ~5–10 min). Don't run checks while a full sweep is running: they share the cores and slow each other down.
3. The final number is the top 11 replayed on fresh seeds (`--top 11 --seed 101 --runs 3`), since ranking and scoring builds on the same seeds flatters them. Rerun a full sweep only for classes whose spells changed enough to reshuffle the ranking.
4. A full sweep splits cleanly by `--classes`, so cloud sessions (one class each) can run it in a quarter of the time when it's worth the setup.

**Batch sims:** `tools/simulate.sh` (needs `$GODOT`) runs N seeded runs per class × movement mode in parallel and prints win %, average wave, kills, hits and gold. Flags after `--` go to every run. Each launch is single-threaded, so it runs launches in parallel (`-j`, default 8): 80 five-wave runs (4 classes × 2 modes × 10, `-- --waves=5`) take about 90s on the Mac; 20-wave runs take up to ~4× longer.

```bash
tools/simulate.sh -n 20 -m circle,smart                 # every class, both movement modes
tools/simulate.sh -c mage -n 30 -o <scratch>/sims -- --spells=Fireball,Blizzard,Blink   # keep raw logs
```

`--quit-after` is a safety net (a 20-wave run is ~70k frames at 60 fps, so allow ~90000 per run): Autoplay is C#, so if the C# assembly fails to load (build missing, wrong .NET), nothing quits the game. `run_start` logs the .NET runtime version. Events: `run_start` (class, spells, gear, `retry=true` when started by Retry), `damage` (at run end: damage landed per source — weapon, spell or minion type — via `Combat.Damage`, the same numbers the in-game meter shows; the tool for spell tuning), `healing` (at run end: HP regained per source via `Combat.Healing`: potions, hearts, HP Regen, healing spells, life steal per ability, barrier absorption), `wave_start`, `wave_end` (kills, gold, bag, hp, potions, reserve, buff potions, `peak_enemies` alive at once), `offers` (each shop roll: items with rarity and price), `buy` (rarity, scaled stats, what it replaces and the refund), `reroll` (smart/random shop), `potion` (source charge/bought/reserve, hp before, heal), `heart` (healed, added to reserve, hp, reserve after), `drink` (buff potion; Autoplay drinks one when 5+ enemies are alive and it isn't active), `run_end` (result, wave, kills, gold, gear, trinkets, hits/dodged/regen/shielded; items logged as `Name[rarity]`), `error`. Career adds `career` (save path, load status, level, xp, free points, talents, heirloom, record; logged on the talents screen), `talent` (each point spent), `heirloom` (gear and rarity kept after a victory) and `career_end` (the character once the run is banked). `--tour` adds `tour step=…` (fails with `error tour: …` if a screen didn't open, close or pause as expected). The `GameSettings` autoload prints `[settings] PATH: fresh|loaded` (or `in memory (autoplay)`) with the values. The `Career` autoload prints `[career] save PATH: fresh|loaded|migrated|corrupt|newer`. Never point `--save` at `user://career.json`. Bad flags log `error` and exit with code 1. To measure something new, add a temporary `GD.Print` where it happens, run with fixed seeds before and after the change, compare, then remove the print. If a test needs control Autoplay doesn't offer yet, add a flag to `AutoplayOptions` rather than a throwaway hook.

## Architecture

- `scenes/<feature>/` holds a `.tscn` scene paired with its `.cs` script. `scripts/` holds shared, scene-less code. `data/` holds `.tres` Resource files (game content).
- `Main.cs` is the run controller and the only place signals get wired together. It emits `RunStarted`/`WaveStarted`/`WaveEnded`/`RunEnded`, and when launched with `--autoplay` it adds the `Autoplay` debug driver (`scripts/debug/`), which uses each screen's exposed buttons (`ModeSelect`/`ClassSelect.Choices`, `CareerScreen.TalentButtons`, `Shop.Offers`/`ContinueButton`, `CareerSummary.HeirloomChoices`/`RetryButton`, `Hud.RetryButton`, the pause menu and settings buttons for `--tour`) to press real buttons. Its flow is ModeSelect → ClassSelect (Back returns to ModeSelect) → [career: CareerScreen] → SpellSelect (Back returns one step) → Wave → Shop → Wave … → Victory or Defeat (arcade: HUD end screen with Retry / Choose class buttons; career: `CareerSummary`, same two buttons). The tree is paused whenever a wave isn't running. The UI layers (`ModeSelect`, `ClassSelect`, `CareerScreen`, `SpellSelect`, `Shop`, `CareerSummary`, `Hud`, `PauseMenu`, `GearScreen`, `SettingsScreen`) are `process_mode = Always`, so they still work while paused. Restart (R, "Choose class" on the end screens, or Abandon run in the pause menu) reloads the scene; the mode survives in the `Career` autoload, so it lands on class select in the same mode. **Retry same class** (end screens, pause menu) stores `Career.PendingRetry` (class and spell `Id`s), reloads, and `Main._Ready` starts that run straight away, skipping every select screen (career: the talents screen too). Abandoning or retrying mid-run banks nothing in career.
- **Overlays:** `PauseMenu` (Esc, during a wave or the shop), `GearScreen` (Tab, waves only, read-only) and `SettingsScreen` (from the pause menu or mode select) are `process_mode = Always` CanvasLayers built in code (layers 5/5/6). Each handles its keys in `_Input` and calls `SetInputAsHandled`; Main decides when they may open (`CanOpen` delegates) so they never stack. Pause and gear screen set `GetTree().Paused = true` on open and restore the previous value on close, so pausing over the (already paused) shop keeps it paused. Centered menus keep on screen with `ScreenFit.Attach(layout)` (`UiStyles.ScreenLayout` does it for you): it shrinks the layout around its center when the content is taller or wider than the window. `GearViews` holds the equipment listing and stat lines shared by the shop and the gear screen; worn gear is a `PaperDoll` (slot boxes on a body silhouette, positions in `PaperDoll.SlotPositions` per `Equipment.Layout` entry, so a new slot needs a spot there). Damage and healing meters: `Combat.Damage` and `Combat.Healing` are `MeterLog`s (run totals per source name, a wave-start snapshot, bar colors). `Combat.Deal` fills damage; `Player` fills healing at every heal (`Heal(amount, source, color)` for potions and healing spells, `StealLife` per ability as "X (life steal)", HP Regen, Hearts, and barrier absorption as "X (barrier)"), counting only HP actually regained. `Main.StartRun` resets both (`Combat.ResetMeters`), `StartWave` snapshots them (`Combat.MarkWaveStart`), and `Combat.RegisterSource` gives weapons, spells and their minions their damage bar colors. `CombatMeters` shows them: on the HUD (left side) damage and healing stacked for the current wave; in the shop, one at a time behind Damage/Healing and Last wave/Whole run tabs. Each `CombatMeter` reads its log every 0.25s on its own.
- **Settings:** `GameSettings` autoload (`scripts/settings/`, `GameSettings.Instance`): fullscreen (also F11 / Alt+Enter, handled by the autoload on any screen), screen shake 0–1 (scales `ShakeCamera`'s offset), enemy damage numbers on/off (checked in `Enemy.TakeDamage`), master volume (sets the Master audio bus; no audio yet). Saved to `user://settings.cfg` (`ConfigFile`) on every change; never touches the career save. Under Autoplay it uses defaults in memory unless `--settings=PATH`, so seeded runs don't depend on the player's settings.
- **Controls:** WASD/arrows move, 1–4 cast (Shift+key or right-click toggles auto-cast), Space drinks a potion, 5/6 buff potions, Tab gear screen, Esc pause menu, F11 or Alt+Enter fullscreen, R on an end screen = choose class. Input actions live in `project.godot` (`pause`, `gear_screen`, `toggle_fullscreen` among them).
- **Classes:** `ClassData` Resource (`data/classes/`) holding base max HP, move speed and armor, a `StartingWeapon` item (any weapon in the catalog), an optional weapon trait applied to whatever weapon is equipped (`WeaponLifeSteal`; `WeaponRaiseMinion` + `WeaponRaiseChance`, set on the weapon's `AbilityContext`; weapons themselves stay free of class mechanics), the class's full spell list (8 each), and `SpellPicks` (how many the player picks, max 4). `SpellSelect` shows the list in a 4-column grid; pick order is slot order. `Player.Setup(classData, pickedSpells)` must run before `ApplyStats`. Classes appear on the select screen only once they're listed in `Main.tscn`'s `Classes` array.
- **Abilities:** each class's weapon is its always-on basic attack; spells are stronger attacks on longer cooldowns. Both are `AbilityData` Resources (`data/weapons/`, `data/spells/`). Every spell has an `Id` (file name; checked for empty/duplicates at startup with the save Ids). Each subclass holds both the tuning values and the behavior: `ProjectileAbility` (optionally explodes; also volleys of `Count`, `Pierce`, `Returns` like a boomerang, `Homing` per shot, and a `Shape` for the look), `AreaAbility` (around the caster or at a target point; target-point auto-casts aim at the densest crowd, and `Delay` > 0 telegraphs the spot with a `DelayedBlast` first, like Meteor), `MeleeArcAbility`, `ChainAbility` (instant hit that jumps between enemies), `ChargeAbility` (ground dash via `Player.Leap(..., airborne: false)` that hits along its path), `BuffAbility` (an `AreaAbility` shove plus timed stat modifiers on the caster; optional `HealthCost`, like Blood Pact), `DrainAbility` (a `DrainBeam` tether that ticks damage and retargets), `SummonAbility` (spawns minions), `LineAbility` (instant strike along a line from the caster, e.g. Shockwave), `AuraAbility` (an `AuraField` that ticks for `Duration`, following the caster or fixed at the densest crowd; `Damage` is per second), `BlinkAbility` (a `LeapAbility` that blasts where you *left*; auto-cast escapes the crowd), `DetonateAbility` (Corpse Explosion: blows up `Detonatable` minions; scales with Minion Damage). `BuffAbility` can also grant a `Shield` (a barrier on `Player.AddShield` that absorbs damage after armor) and wait for `CastBelowHealth`. A new ability with existing behavior is a new `.tres`; a new kind of behavior is a new subclass that overrides `TryAutoTarget` and `Cast`. `LeapAbility` moves the player via `Player.Leap` (untouchable while airborne), then blasts where it lands. Abilities that move the player should set `AutoCastByDefault = false`. Resources are shared, so runtime state (cooldown, auto-cast on/off) lives in `AbilitySlot`.
- **`AbilityCaster`** (child of Player) always auto-fires the weapon, and auto-casts each spell slot that has auto-cast on. Keys 1–4 (`ability_N` actions) cast manually, aiming at the mouse when `NeedsAim` is true. Shift+key or right-clicking a hotbar slot toggles auto-cast. Damage% applies to all abilities, AttackSpeed% only to the weapon's cooldown, and Range to all (melee gets half). Auto-targeting (`Combat.NearestEnemy`) skips enemies that are `IsDoomed`: a projectile cast at an enemy reserves its damage there (`Projectile.ReserveOn`) until it lands, so shots don't overkill. Hit side effects (slow, knockback, stun, DoT — optionally spreading to `DotSpreads` neighbors when the host dies — raise-on-death mark) and crit odds are `HitEffects`, applied through `Combat.Hit` and `Combat.DamageArea`; the matching `AbilityData` exports are in its On Hit / On Kill groups. DoTs tick on the `Enemy` (strongest wins, every 0.5s, tinted numbers). Crit is rolled per enemy in `Combat.Hit` from the ability's `CritChance` (percent, plus the Crit Chance stat) and `CritMultiplier`; there's deliberately no global crit damage stat (see `Goals.md`).
- **Life steal:** every player hit ends in `Combat.Deal`, which heals `Player.StealLife` for `HitEffects.LifeSteal` (ability's `LifeSteal` % + the Life Steal stat) of the damage that landed (no overkill). `StealLife` is capped at `Player.LifeStealCap` HP/s (token bucket) and batches the "+N" text. DoT ticks steal too; minion hits don't. Life steal stays a Warlock thing on spells and stats: only Warlock spells have a base `LifeSteal` and the Life Steal stat comes only from Blood Pact's buff, so don't add the stat to catalog items. Weapons have none either: the Warlock's weapons steal through its class trait (`ClassData.WeaponLifeSteal`, added to the weapon's `AbilityContext` only).
- **Minions:** `Minion` (`scenes/minions/`, built in code like pickups) driven by a `MinionData` Resource (`data/minions/`). `ShotSpeed` + `ProjectileScene` make a ranged type (Skeletal Mage) that shoots from `AttackReach`. Spawned by `Minion.Spawn` (deferred) from `SummonAbility` or from an enemy that dies while marked (`HitEffects.RaiseMinion`, `Enemy.MarkForRaising`). Chases the nearest enemy within a leash of the player, else follows the player. Damage = `MinionData.Damage` × `AbilityContext.MinionDamageMultiplier` (Damage% + Minion Damage%), read live from `Player.Abilities.Context`. Cap per type (`MaxAlive`, oldest crumbles) and `Lifetime`. `MinionData.Targetable` (on for all current types) puts the minion in `Groups.EnemyTargets` next to the player: enemies retarget to the nearest member every 0.25s (`Enemy.FindTarget`), their contact hurts it (distance check, i-frames) and enemy shots hit it (`Minion : IDamageable`; enemy shot mask includes layer 5). A non-targetable minion is ignored, can't be hurt, and enemy shots pass through it (`Projectile.Impact` skips it). In `Groups.Minions` + `Groups.Transient`, so they clear at wave end. Physics layer 5 (minions): collide with walls and each other only.
- **Run state:** `RunState` is plain C#, owned by `Main`. It holds wave, gold, kills, owned items and `PlayerStats`. A scene reload discards it; anything that must outlive a run lives in the `Career` autoload.
- **Career (`scripts/career/`):** `Career` is an autoload (`project.godot` `[autoload]`, reached via `Career.Instance`) holding the session's `GameMode`, a pending retry and the save. The save (`CareerSave`: one `CareerCharacter` per class `Id`) loads lazily on first career use, so arcade never touches it, and `Persist()` writes it after every change. `CareerStore` does the JSON I/O: temp file then replace; a missing file starts fresh; an unreadable or newer-version file is moved aside (`.corrupt-…`/`.newer-…`) and a fresh career starts. The save stores facts only (total XP, talent ranks, heirloom item id, record); levels and points derive from `CareerSettings` (`data/career/CareerSettings.tres`: XP rewards, level curve, `CareerTalent` list), so retuning needs no migration. Unknown JSON fields are kept (`[JsonExtensionData]`). Characters are keyed by `ClassData.Id` and the heirloom is an `ItemData.Id` (consumables inherit it); talents by `CareerTalent.Id`. `Main._Ready` calls `Career.ValidateIds`, which logs an error for an empty or duplicate `Id`, so give every new class/item a unique one. Never change an `Id` once shipped; `.tres` file names are free to change. Bump `CareerSave.CurrentVersion` only for breaking changes, with a step in `CareerStore.Migrate`. A career run gets talents via `RunState.GrantStat` and the heirloom via `AddItem` (`Main.ApplyCareer`); `Main.EndCareerRun` banks XP and saves before showing `CareerSummary`.
- **Stats:** `StatType` enum plus `PlayerStats` (summed bonuses; percent stats stored as whole numbers). `Player.ApplyStats(runStats)` takes base values from the `ClassData` and layers the bonuses on top. Call `ApplyStats` again whenever run stats change. Timed bonuses live in `Player.Buffs` (`ActiveBuffs`): `Player.AddBuff` adds one, and the player adds them into a copy of the run stats, re-applying when one starts or expires. Buffs clear at each wave start. `StatType` values are serialized as integers in `.tres` files: add new entries, but never renumber existing ones. `StatInfo` holds labels, formatting and caps: `StatInfo.Cap`/`Capped` (Cooldown Reduction 50%, Dodge 60%; totals above the cap are kept but do nothing), item descriptions add a "caps at" note, and the shop's stats panel lists only non-zero stats. Cooldown Reduction scales spell slots' `CooldownMultiplier` only (the weapon has Attack Speed). HP Regen is HP per 10s (`StatInfo.RegenPeriod`), healed every frame in `Player.UpdateRegen` with a batched green "+N"; it never fills the potion reserve. Dodge is rolled in `Player.TakeDamage` (contact and enemy shots) only when the chance is above 0, so runs without it draw the same random numbers; a dodge shows "Dodge" and starts i-frames like a hit. `Player.HitsTaken`/`HitsDodged`/`RegenHealed` feed Autoplay's `wave_end`/`run_end` (`hits=`, `dodged=`, `regen=`).
- **Items:** `ItemData` (a `[GlobalClass]` Resource holding `StatModifier` sub-resources), one `.tres` per item in `data/items/`. An item only shows up in the shop once it's listed in `data/ItemCatalog.tres` (weapons too: any class can buy any weapon). A catalog item whose value is class-specific (e.g. Minion Damage) lists the class `Id`s it's offered to in `ItemData.Classes` (empty = every class); `Main.ShopPool` filters by it, `--item=` grants don't. An item with `Slot = None` is a stacking trinket (`RunState.Trinkets`); any other `EquipSlot` makes it gear, worn in `RunState.Equipment` (6 positions in `Equipment.Layout`, Ring twice). `Equipment.TargetsFor`/`Displaced`/`Equip` hold the swap rules (two-handers, starting-weapon fallback); the shop refunds `Equipment.RefundFor` for what was replaced (`SellValue`, but nothing for the free starting weapon). A main-hand item's `Weapon` (an `AbilityData` in `data/weapons/`) is the basic attack: `Main.ApplyLoadout` calls `Player.SetWeapon` then `ApplyStats` after every purchase, and `Hud.SetWeapon` (the `WeaponSlotView` left of the spell bar: name in rarity color, refill bar, tooltip). `RunState.Stats` is recalculated from gear, trinkets and grants, never edited directly (use `GrantStat`). Consumables are `ConsumableData : ItemData` (`data/consumables/`, listed in the catalog's `Consumables`): `RunState.AddPotion` puts them in `RunState.Potions`, and the shop sells them on a fixed potion shelf (not rerolled) up to `MaxCarry`. Consumables have no rarity.
- **Rarity:** owned and offered items are `ItemInstance`s (plain C#: the shared `ItemData` + a `RarityTier`), never mutated `ItemData`s, since Resources are shared. `RunState.Equipment`/`Trinkets`, refunds, the shop and the career heirloom all hold instances; the swap rules (`TargetsFor`/`Displaced`) take the `ItemData`. Tiers (`Rarity` enum: Common, Uncommon, Rare, Epic; saved by name, so never rename one) are tuned in `data/RaritySettings.tres` (`RaritySettings` → one `RarityTier` each: color, `StatMultiplier` for positive modifiers only, rounded and at least +1 over Common, `PriceMultiplier`, `WeaponDamageMultiplier`, and odds `Chance` + `ChancePerWave` up to `MaxChance`; Common gets the remainder). The shop rolls a tier per offer with `RaritySettings.Roll(wave)` (rerolls roll again) and shows the odds under the gold. Weapon rarity scales only the basic attack, through a separate weapon `AbilityContext` in `AbilityCaster` (`Player.SetWeapon(weapon, damageMultiplier)`). Starting weapons are always Common. Use `ItemInstance.Color`/`SlotLabel`/`Tooltip()` when showing an owned item so the tier colors stay consistent. The career save stores the heirloom's rarity as `heirloomRarity` (missing = Common).
- **Waves:** `WaveSettings.For(wave)` is a formula giving duration, spawn rate and enemy health/damage/speed scaling. `EnemySpawner.Begin` takes the settings and `Enemy.ApplyWave` scales each spawn.
- **Enemies:** every type shares `Enemy.tscn`. An `EnemyData` Resource (`data/enemies/`) sets shape, stats, knockback resistance, spawn settings (`FirstWave`, `SpawnWeight`) and an optional ranged attack (`ShotRange > 0` makes the enemy keep its distance and shoot). The spawner sets `enemy.Data` before `AddChild` and picks types by weight from those unlocked for the wave. A type only spawns once it's listed in the Spawner's `EnemyTypes` in `Main.tscn`. Enemies chase the nearest of `Groups.EnemyTargets` (player or targetable minion). Enemy shots reuse `Projectile` with `CollisionMask` set to world + player + minions.
- **Pickups:** `Coin` and `Heart` extend `Pickup` (`scenes/pickups/`), which flies to the player once they're within `PickupRange` and calls `Collect()`. Override `Wanted` to make a pickup wait (an attracted pickup that stops being wanted drops where it is). `Heart` calls `Player.CollectHeart`: heals when hurt (overflow into the reserve), fills the reserve at full HP, and waits (`Player.WantsHeart`) only while HP and reserve are both full. Enemies drop a heart with `EnemyData.HeartDropChance`. `Player.Heal` shows the green "+N".
- **Potions:** `PotionBelt` (plain C#, `RunState.Potions`, handed to `Player.Setup`) holds free charges (`PotionsPerWave`, refilled by `Main.StartWave` → `RefillPotions`), bought consumables, and the heart-filled reserve (capacity = `Player.PotionHeal`, kept between waves). `Player.UsePotion` (Space, `use_potion`) skips at full HP, else drinks a full reserve first, then a full potion (free charge, then bought) for `PotionHeal`, else the whole partial reserve; `Player.NextPotion` says which. Buff potions (`PotionBelt.Hotbar`, catalog order) are keys 5, 6… (`consumable_N` actions) and go through `Player.AddBuff`. `PotionHeal` = `BasePotionHeal` + the Potion Heal stat. `Hud.BindPotions` adds the slots (`PotionSlotView`: Health, Reserve, Buff) after the spell bar.
- **Gold:** enemies drop a `Coin` when they die (added deferred, because death happens inside a physics callback). Pickups and projectiles are in `Groups.Transient` and get cleared at wave end. Before that, `Main` adds the floor coins' value to `RunState.Bag`, and each later pickup draws the same amount again from the bag (doubling it) until it's empty.
- Cross-entity lookups use **groups** (`Groups.Player`, `Groups.Enemies`), not node paths. Damage goes through `IDamageable`, and entities hand it to a child `Health` node that emits `Changed`/`Died`.
- `Arena` is the single source of truth for play bounds: the rect from (0,0) to `Size`. It builds its own wall collision in code.
- `EnemySpawner` places a `SpawnMarker` (a blinking X warning) first, then spawns the enemy as its own child. Spawn interval goes from `StartInterval` to `EndInterval` as `Progress` (0 to 1, set by `Main`) increases. `Clear()` removes everything.
- **Sprites:** `ClassData`/`EnemyData`/`MinionData` have an optional `Sprite` (`Texture2D`, placeholder SVGs in `art/`: 64×64 viewBox, authored facing right, dark outline) and `SpriteScale` (drawn size = body diameter × scale). Each entity draws it from its own `_Draw()` through `SpriteArt` (mirror when moving left, floor shadow, `SpriteArt.Flash` overbright modulate for hit flash, status tints multiply from white); unset falls back to the old shapes. SVGs are imported with mipmaps (`mipmaps/generate=true` in the `.import`) and drawn with `TextureFilter = LinearWithMipmaps`, so they stay smooth scaled down. A new SVG needs one `--import` run, then flip mipmaps in its `.import`.
- **Game feel:** `AreaFlash`, `LineFlash` (charge paths, jagged lightning), `FloatingText` (damage numbers, pickup cues) and `DeathPop` (`scenes/effects/`) are fire-and-forget visuals with a static `Spawn(...)` that adds them deferred and puts them in `Groups.Transient`. `Enemy.TakeDamage` spawns damage numbers and the hit pop; `EnemyData.ShowHealthBar` draws a bar once damaged. Screen shake is trauma-based: `ShakeCamera.Shake(tree, trauma)` (0–1). Abilities set it with the `ScreenShake` export, applied when an area lands or a projectile explodes.
- Projectiles and `AreaFlash` effects are added to `CurrentScene`, not the player, so they don't move with it. Add them deferred when spawning from a physics callback.
- **Physics layers** (named in project.godot): 1 world, 2 player, 3 enemies, 4 projectiles, 5 minions. Bitmask values are 1, 2, 4, 8, 16. Enemies collide with walls and each other, not the player. Contact damage comes from the player's `Hurtbox` Area2D, with i-frames.
- Balance numbers are `[Export]` properties, editable in the Inspector or in the `.tscn` files.

## Godot C# conventions to follow

- Script classes must be `partial` and the class name must match the file name.
- Signals: `[Signal] public delegate void SomethingHappenedEventHandler(...)`; emit with `EmitSignal(SignalName.SomethingHappened, ...)`.
- `[Export]` fields only appear in the editor after a C# build.
- `.tscn`/`.tres` are text and can be edited directly, but keep `uid://` references and `ext_resource` ids consistent. Commit the `.uid` files Godot generates next to scripts/resources. `.godot/` is generated and ignored.

## Game design and project tracking

Read both of these at the start of a session:

- **`Goals.md`:** the original vision (a rough, non-binding brainstorm, so treat it as a baseline rather than a spec) plus a **"Decisions so far"** section. Once something is decided, record it there so it doesn't get debated again.
- **`ROADMAP.md`:** what's done (with commits), the suggested next steps, the backlog of ideas, open design questions, and known issues.

The game in brief: a fantasy arena-survivor (Brotato / Vampire Survivors style) with an RPG layer of classes, spells, equipment slots and potions.

**Workflow:** at the end of each feature, update `ROADMAP.md` (and the decisions in `Goals.md` if any were made) in the same commit as the feature.
